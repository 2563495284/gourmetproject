# 随机种子与随机机制说明

本文基于当前代码实现整理，重点覆盖随机种子的生成、派生、业务随机流使用方式，以及现阶段可能影响“同种子同结果”的问题。

## 1. 总体结论

当前项目已经有一套独立的确定性随机系统，核心实现位于：

- `Assets/GameMain/Scripts/Core/Random/RandomService.cs`
- `Assets/GameMain/Scripts/Core/Random/Xoshiro256SS.cs`
- `Assets/GameMain/Scripts/Core/Random/SplitMix64.cs`
- `Assets/GameMain/Scripts/Core/Random/SeedDomains.cs`
- `Assets/GameMain/Scripts/Core/Utility/StableHash.cs`

整体方向是正确的：

- 不依赖 `UnityEngine.Random` / `System.Random` 做玩法随机。
- 用稳定哈希解析字符串种子，避免 `string.GetHashCode()` 的跨平台不稳定。
- 用 xoshiro256** 作为确定性 PRNG。
- 用 SplitMix64 从主种子派生子种子。
- 用“系统域 + 实例 key”拆分随机流，降低不同系统之间互相污染的概率。
- 有专门的 `RngDeterminismTests` 覆盖同种子一致、不同流隔离、快照恢复等基础行为。

随机快照已经接入存档链路（这是相对早期版本的重要更新）：

> `RunSaveData` 已包含 `RandomSnapshot` 字段。`RunPersistence.Save` 在写档前调用 `GameApp.Random.Capture()` 把所有非 cosmetic 流的当前状态一起保存；`RunPersistence.TryLoad` 优先 `GameApp.Random.Restore(data.RandomSnapshot)`，只有旧档没有快照时才 fallback 到 `Init(SeedText)`。

也就是说，“同种子 + 同操作 + 可中途读档续上”的基础已经具备：依赖“流消费进度”的随机（包括经营挑战 `combat`/`recipe` 流）读档后会从保存时的消费位置继续，而不是回到流起点。同时商店库存、奖励 offer、行动候选这类 UI 触发的随机，也通过 `GameRun` 的 `Pending*` 缓存写入存档（见 §5），避免 UI 重开/读档重算。

早期文档列出的少数业务口径问题（离开商店同日再进重掷、Boss key 粒度偏粗、`Range` 非法区间静默兜底）也已在代码中处理，详见 §7。目前没有已知影响“同种子同结果”的待办风险。

## 2. 种子入口

### 2.1 新开局种子

新开局在 `ProcedureGameplay.StartNewRun` 中生成：

```csharp
string seed = $"{characterId}-{DateTime.UtcNow.Ticks:x}";
GameApp.Random.Init(seed);
var run = new GameRun(tables, db, characterId, seed, weekIndex: 1);
```

也就是说，默认种子由经营方向 id 和当前 UTC ticks 组成，例如：

```text
dog-8dc354e0f2c1234
```

该文本同时写入 `GameRun.SeedText`，并在存档中保存。

### 2.2 字符串种子解析

`RandomService.ParseSeed` 规则：

- 空字符串返回 `0UL`。
- 纯数字字符串按 `ulong` 数值解析。
- 非纯数字字符串走 `StableHash.Fnv1a64(seedText)`。

这里没有使用 `GetHashCode()`，是正确选择。`StableHash.Fnv1a64` 按 UTF-16 字节做 FNV-1a 64 位哈希，跨平台稳定。

### 2.3 空种子

`RandomService.Init(string seedText)` 收到空白字符串时会调用 `GenerateRandomSeedText()` 生成 8 位可分享文本。

不过当前新开局流程没有走空种子入口，而是自己用 `characterId + ticks` 生成种子。

## 3. 随机流派生机制

### 3.1 主种子

`RandomService` 保存两个值：

- `SeedText`：玩家可见/可分享的原始种子文本。
- `MasterSeed`：由 `SeedText` 解析出的 64 位主种子。

### 3.2 普通命名流

`RandomService.Stream(name)` 会按下面逻辑生成流：

```text
MasterSeed + streamName
  -> StableHash.Fnv1a64(streamName)
  -> hash_combine 风格混合
  -> SplitMix64.Mix
  -> Xoshiro256SS(seed)
```

同一个 `name` 会被缓存，后续再次取到的是同一条流的当前状态，而不是重新开始。

### 3.3 域流

业务层主要使用 `DomainStream(domain, instanceKey)`：

```text
MasterSeed
  -> domainSeed = DeriveStreamSeed(MasterSeed, domain)
  -> instanceSeed = DeriveStreamSeed(domainSeed, instanceKey)
  -> Xoshiro256SS(instanceSeed)
```

缓存 key 为：

```text
domain + '\u0001' + instanceKey
```

这种两段派生比简单拼字符串更规整，也能让系统域之间天然隔离。

### 3.4 系统域

当前 `SeedDomains` 包含：

- `map`：每周时间轴 / 关卡布局。
- `action`：行动组调度与 n 选一候选。
- `effect`：行动 / 事件效果结算。
- `event`：随机事件抽取与选项结算。
- `boss`：星级评鉴抽取。
- `shop`：商店非装饰品和消耗品随机，如食物、碎片、槽位。
- `loot`：装饰品和消耗品池抽取，和商店其它随机隔离。
- `reward`：过关奖励。
- `recipe`：经营挑战开局食谱食谱。
- `combat`：局内经营挑战上菜 / AI。
- `cosmetic`：表现层随机，不入存档。

域拆分是当前随机系统最重要的设计点：调整商店装饰品和消耗品数量不应影响食物池；调整表现特效不应影响经营挑战结果；调整 星级评鉴消耗不应污染奖励流。

## 4. PRNG 实现

### 4.1 Xoshiro256SS

`Xoshiro256SS` 是 xoshiro256**：

- 内部状态为 4 个 `ulong`，共 256 bit。
- 单个 64 位 seed 通过 SplitMix64 展开成 256 位状态。
- 检查并规避全零状态。
- `NextUInt()` 取 `NextULong()` 的高 32 位。
- `NextFloat()` 取高 24 位映射到 `[0, 1)`。
- `NextDouble()` 取高 53 位映射到 `[0, 1)`。

这套实现适合玩法确定性随机，不适合密码学安全随机。

### 4.2 整数区间

`Range(int minInclusive, int maxExclusive)` 使用 Lemire 无偏算法，避免简单取模造成的分布偏差。

注意当前行为：

```csharp
if (maxExclusive <= minInclusive)
{
    return minInclusive;
}
```

非法区间不会抛错，而是返回下界。这对业务容错友好，但如果配置写错，问题可能被静默吞掉。

### 4.3 权重随机

`WeightedPickIndex(weights)` 规则：

- 只累计 `w > 0` 的权重。
- 总权重小于等于 0 时抛异常。
- 用 `NextDouble() * total` 落点。
- 浮点误差兜底返回最后一个下标。

业务层很多地方会把 `<= 0` 权重改成 `1`，例如行动、商店、Boss。这个口径与部分配置说明中“<=0 运行时按 1 处理”一致。

## 5. 主要业务随机点

### 5.1 时间轴

入口：`WeekLoopController.BeginWeek`

```csharp
GameApp.Random.DomainStream(SeedDomains.Map, $"w{_run.WeekIndex}")
```

用途：

- 当前周没有时间轴，或上一周已走完时，按周随机时间轴。
- `TimelineService.RollWeekTimeline` 筛选候选后按权重抽取。
- 抽取结果写入 `GameRun.CurrentTimelineId` 和 `TimelineLengthDays`。

这个设计较安全，因为随机结果写入了运行态和存档，读档后优先沿用已保存时间轴。

### 5.2 行动选择

入口：`WeekMapForm.RollChoices`

```csharp
GameApp.Random.DomainStream(
    SeedDomains.Action,
    $"r{run.RunActionStepIndex}_w{run.WeekIndex}_d{run.CurrentDay}_s{run.ActionStepIndex}")
```

用途：

- `ActionScheduleService.EnsureCurrentGroup` 逐行动生成整局行动组序列：先检查本周逐行动累计下限，再检查累计上限，否则按本周权重完全放回随机。
- 从当前大组里按小组权重选 1 个小组，将其固定成员过滤后展示为最多 3 个行动。
- 同时普通行动耗时。

注意点：

- 行动组序列会保存到 `GameRun.ActionGroupSequence`，这部分可读档恢复。
- 大组计数只统计当前周已经实际写入序列的项；换周后从 0 重新统计。上下限缺项、负数或索引越界均视为不限制。
- 候选行动已做 pending 缓存：`WeekMapForm.RollChoices` 先按 key 查 `run.HasPendingActionChoices(key)`，命中则直接复用，不再消费 action 流；首次掷出后 `SetPendingActionChoices` + `RunPersistence.Save`。所以同一步 UI 重开/读档会看到同一组选项。
- 玩家在 `Choose` 选定后才 `ClearPendingActionChoices`，进入下一步重新掷。这正是早期版本缺失、现已补上的“UI 重开保持一致”行为。

### 5.3 行动效果

入口：`WeekLoopController.OnActionPicked`

```csharp
GameApp.Random.DomainStream(
    SeedDomains.Effect,
    $"exec_r{context.RunStepIndex}_w{_run.WeekIndex}_s{context.StepIndex}_{context.ActionGroupId}_{context.Action.Id}")
```

用途：

- 执行行动带来的随机效果。
- key 包含整局行动序号、周、本周行动序号、行动组、行动 id，隔离度较好。

### 5.4 事件

入口包括：

- 时间轴事件节点：`event/node_w{week}_d{node.Day}`
- 行动触发随机事件：`event/action_w{week}_d{day}_s{step}`
- 事件选项结算：`event/resolve_w{week}_d{day}_{eventId}`

用途：

- `EventService.RollEvent` 按权重抽事件。
- `ResolveImmediate` / `ResolveOption` 结算事件效果。

注意点：

- 不可重复事件通过 `UsedEventIds` 记录。
- 如果同一天同事件 id 被不同来源重复 resolve，`resolve_w..._{eventId}` 这条流会继续消费旧状态，而不是重新开始。是否合理取决于设计是否允许这种重复路径。

### 5.5 Boss

入口：`WeekLoopController.HandleBossNode`

```csharp
GameApp.Random.DomainStream(SeedDomains.Boss, $"w{_run.WeekIndex}_{node.Id}")
```

用途：

- 按解锁条件筛选 Boss。
- 从未抽取 星级评鉴候选中按权重抽一个；候选取光后重置抽取历史。

现状：

- key 已包含时间轴节点唯一 id（`node.Id`），同一周即便存在多个 星级评鉴节点也各自独立抽取，不再共用同一条流按调用顺序续掷。早期“key 只有周”的粒度问题已修复。

### 5.6 商店

入口：`ShopForm.RollStock`

```csharp
shop: GameApp.Random.DomainStream(SeedDomains.Shop, $"w{week}_d{day}")
loot: GameApp.Random.DomainStream(SeedDomains.Loot, $"shop_w{week}_d{day}")
```

用途：

- `loot` 抽被动/消耗品。
- `shop` 抽食物和餐桌格。
- 装饰品随机流与其它内容隔离，这是正确的。

现状（已做 pending 缓存）：

- `RollStock` 先按 `_shopKey = GameRun.BuildShopKey(week, day)`（即 `w{week}_d{day}`）查 `run.HasPendingShopStock(key)`，命中则复用缓存库存，不再消费 shop/loot 流。
- 首次掷出后 `SetPendingShopStock` + `RunPersistence.Save`；购买后也会同步 `SetPendingShopStock` 并存档（只移除已购项，不重掷）。
- 因此 `OnOpen` 虽然每次都调用 `RollStock()`，但在 pending 命中时不会改变库存；读档后同一天再进商店，会恢复离开前的剩余库存。
- 点击“离开”（`OnLeaveClicked`）只 `Save` 后关闭，**不再清空** pending 库存。库存按 `w{week}_d{day}` key 持久化，离开后同日再进沿用同一份库存，关闭了“反复进出刷新商品”的可刷点。
- pending 库存在进入下一刷新点（新时间轴 `GameRun.BeginTimeline`，会切换周/天 key 并清空 pending）时自然失效，下一个商店重新掷库存。

### 5.7 奖励

入口：`RewardForm.OnOpen`

```csharp
// 有行动上下文时（经营挑战过关常见）
GameApp.Random.DomainStream(
    SeedDomains.Reward,
    $"r{context.RunStepIndex}_w{week}_d{day}_s{context.StepIndex}_{context.ActionGroupId}_{context.Action.Id}")
// 无行动上下文时 fallback
GameApp.Random.DomainStream(SeedDomains.Reward, $"w{week}_d{day}")
```

key 由 `GameRun.BuildRewardKey` 生成，有效行动上下文时使用长 key，包含整局行动序号、周、天、本周行动序号、行动组、行动 id，隔离度较好。

用途：

- 随机金币区间。
- 抽主奖励槽位、额外奖励概率、奖励候选。

现状（已做 pending 缓存）：

- `RewardForm.OnOpen` 先按 rewardKey 查 `run.GetPendingRewardOffer(key)`，命中则直接展示，不再消费 reward 流。
- 首次生成 offer 后 `SetPendingRewardOffer` + `RunPersistence.Save`；玩家确认领取后 `ClearPendingRewardOffer`。
- 因此奖励界面重开/读档后展示同一份 offer，金币与奖励候选不再变化。早期版本“key 只有周+天”“offer 不持久化”的问题均已修复。

### 5.8 经营挑战食谱与局内经营挑战

入口：`BattleSessionFactory.Build`

```csharp
recipe: GameApp.Random.DomainStream(SeedDomains.Recipe, key)
combat: GameApp.Random.DomainStream(SeedDomains.Combat, key)
```

用途：

- `recipe` 生成每个食谱槽的开局 deck。
- `combat` 提供局内经营挑战随机。

风险点：

- `RecipeSlotCount` 个食谱槽共用同一条 recipe 流并连续消费。这本身可以接受，但如果未来槽位数量变化，会影响后续槽位 deck。
- 经营挑战过程中途保存/读档：`recipe`/`combat` 流是 `RandomService` 缓存的命名流，`Capture()` 会把它们当前的消费位置一起写入 `RandomSnapshot` 并存档，`Restore()` 读档后从同一位置继续。所以经营挑战流的随机进度已可恢复，不再需要额外单独保存经营挑战流状态（前提是经营挑战的非随机状态如棋盘、分数等也已写入存档）。

## 6. 当前测试覆盖

`RngDeterminismTests` 已覆盖：

- xoshiro 同 seed 逐位一致。
- `RandomService.Stream` 同 seed 同流名一致。
- 不同流名互不污染。
- 域流同 seed / 同 domain / 同 key 一致。
- 不同 domain / 不同 key 不同序列。
- 商店 `shop` 与 `loot` 隔离。
- `cosmetic` 不写入快照。
- `Capture` / `Restore` 后未来序列一致。
- `RunSaveData_CanCarryRandomSnapshot`：`RandomSnapshot` 能随 `RunSaveData` 携带，并在 `Restore` 后续抽一致。

`V2GameplayTests` 已覆盖存档恢复的 pending 数据与本次修复：

- `RunSaveData_RestoresPendingActionChoices`：读档后行动候选保持一致。
- `RunSaveData_RestoresEmptyPendingShopStock`：读档后商店库存（含空库存）保持一致。
- `RunSaveData_RestoresPendingShopStockContent`：读档后非空商店库存的内容（kind/id/name/price）逐项一致——锁定“离开商店后重进/读档不重掷”。
- `RunSaveData_RestoresPendingRewardOffer`：读档后奖励 offer 保持一致。
- `PendingShopStock_ClearedByBeginTimelineNotByActionStep`：商店库存只由刷新点 `BeginTimeline` 清空，`AdvanceActionStep` 不清——锁定“离开不重掷”依赖的刷新语义。
- `BossRoll_PerNodeKeyIsOrderIndependent`：同周不同 星级评鉴节点 key 抽取互不影响、与调用顺序无关——锁定 Boss key 加 `node.Id` 的修复。

缺口：

- 没有端到端 UI 层测试（上述测试在 `GameRun` / 服务数据层验证，未经过实际 Form 生命周期）。

RunSaveData data = run.ToSaveData();
