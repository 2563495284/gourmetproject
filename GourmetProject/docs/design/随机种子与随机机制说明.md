# 随机种子与随机机制说明

本文基于当前代码实现整理，重点覆盖随机种子的生成、派生、业务随机流使用方式，以及现阶段可能影响“同种子同结果”的问题。

## 1. 总体结论

当前项目已经有一套独立的确定性随机系统，核心实现位于：

- `Assets/GameMain/Scripts/Core/Random/RandomService.cs`
- `Assets/GameMain/Scripts/Core/Random/Xoshiro256SS.cs`
- `Assets/GameMain/Scripts/Core/Random/SplitMix64.cs`
- `Assets/GameMain/Scripts/Core/Random/SeedDomains.cs`
- `Assets/GameMain/Scripts/Core/Utility/StableHash.cs`

整体方向是正确的：

- 不依赖 `UnityEngine.Random` / `System.Random` 做玩法随机。
- 用稳定哈希解析字符串种子，避免 `string.GetHashCode()` 的跨平台不稳定。
- 用 xoshiro256** 作为确定性 PRNG。
- 用 SplitMix64 从主种子派生子种子。
- 用“系统域 + 实例 key”拆分随机流，降低不同系统之间互相污染的概率。
- 有专门的 `RngDeterminismTests` 覆盖同种子一致、不同流隔离、快照恢复等基础行为。

但当前落地存在一个主要风险：

> `RandomSnapshot` 已实现，但当前 `RunSaveData` 没有保存随机流状态；读档时只用 `SeedText` 重新初始化随机服务。这与 `RandomSnapshot` 的设计目标不一致，也会让部分依赖“流消费进度”的随机在读档后发生偏移。

如果目标是严格 roguelike 式“同种子 + 同操作 + 可中途读档续上”，建议后续把随机快照接入存档，或者把所有随机结果都在生成时保存进 `GameRun`，避免 UI 重开/读档重算。

## 2. 种子入口

### 2.1 新开局种子

新开局在 `ProcedureGameplay.StartNewRun` 中生成：

```csharp
string seed = $"{characterId}-{DateTime.UtcNow.Ticks:x}";
GameApp.Random.Init(seed);
var run = new GameRun(tables, db, characterId, seed, weekIndex: 1);
```

也就是说，默认种子由角色 id 和当前 UTC ticks 组成，例如：

```text
dog-8dc354e0f2c1234
```

该文本同时写入 `GameRun.SeedText`，并在存档中保存。

### 2.2 字符串种子解析

`RandomService.ParseSeed` 规则：

- 空字符串返回 `0UL`。
- 纯数字字符串按 `ulong` 数值解析。
- 非纯数字字符串走 `StableHash.Fnv1a64(seedText)`。

这里没有使用 `GetHashCode()`，是正确选择。`StableHash.Fnv1a64` 按 UTF-16 字节做 FNV-1a 64 位哈希，跨平台稳定。

### 2.3 空种子

`RandomService.Init(string seedText)` 收到空白字符串时会调用 `GenerateRandomSeedText()` 生成 8 位可分享文本。

不过当前新开局流程没有走空种子入口，而是自己用 `characterId + ticks` 生成种子。

## 3. 随机流派生机制

### 3.1 主种子

`RandomService` 保存两个值：

- `SeedText`：玩家可见/可分享的原始种子文本。
- `MasterSeed`：由 `SeedText` 解析出的 64 位主种子。

### 3.2 普通命名流

`RandomService.Stream(name)` 会按下面逻辑生成流：

```text
MasterSeed + streamName
  -> StableHash.Fnv1a64(streamName)
  -> hash_combine 风格混合
  -> SplitMix64.Mix
  -> Xoshiro256SS(seed)
```

同一个 `name` 会被缓存，后续再次取到的是同一条流的当前状态，而不是重新开始。

### 3.3 域流

业务层主要使用 `DomainStream(domain, instanceKey)`：

```text
MasterSeed
  -> domainSeed = DeriveStreamSeed(MasterSeed, domain)
  -> instanceSeed = DeriveStreamSeed(domainSeed, instanceKey)
  -> Xoshiro256SS(instanceSeed)
```

缓存 key 为：

```text
domain + '\u0001' + instanceKey
```

这种两段派生比简单拼字符串更规整，也能让系统域之间天然隔离。

### 3.4 系统域

当前 `SeedDomains` 包含：

- `map`：每周行动轴 / 关卡布局。
- `action`：行动组调度与 n 选一候选。
- `effect`：行动 / 事件效果结算。
- `event`：随机事件抽取与选项结算。
- `boss`：Boss 抽取。
- `shop`：商店非道具随机，如菜品、碎片、槽位。
- `loot`：道具池抽取，和商店其它随机隔离。
- `reward`：过关奖励。
- `recipe`：战斗开局菜谱牌组。
- `combat`：局内战斗上菜 / AI。
- `cosmetic`：表现层随机，不入存档。

域拆分是当前随机系统最重要的设计点：调整商店道具数量不应影响菜品池；调整表现特效不应影响战斗结果；调整 Boss 消耗不应污染奖励流。

## 4. PRNG 实现

### 4.1 Xoshiro256SS

`Xoshiro256SS` 是 xoshiro256**：

- 内部状态为 4 个 `ulong`，共 256 bit。
- 单个 64 位 seed 通过 SplitMix64 展开成 256 位状态。
- 检查并规避全零状态。
- `NextUInt()` 取 `NextULong()` 的高 32 位。
- `NextFloat()` 取高 24 位映射到 `[0, 1)`。
- `NextDouble()` 取高 53 位映射到 `[0, 1)`。

这套实现适合玩法确定性随机，不适合密码学安全随机。

### 4.2 整数区间

`Range(int minInclusive, int maxExclusive)` 使用 Lemire 无偏算法，避免简单取模造成的分布偏差。

注意当前行为：

```csharp
if (maxExclusive <= minInclusive)
{
    return minInclusive;
}
```

非法区间不会抛错，而是返回下界。这对业务容错友好，但如果配置写错，问题可能被静默吞掉。

### 4.3 权重随机

`WeightedPickIndex(weights)` 规则：

- 只累计 `w > 0` 的权重。
- 总权重小于等于 0 时抛异常。
- 用 `NextDouble() * total` 落点。
- 浮点误差兜底返回最后一个下标。

业务层很多地方会把 `<= 0` 权重改成 `1`，例如行动、商店、Boss。这个口径与部分配置说明中“<=0 运行时按 1 处理”一致。

## 5. 主要业务随机点

### 5.1 行动轴

入口：`WeekLoopController.BeginWeek`

```csharp
GameApp.Random.DomainStream(SeedDomains.Map, $"w{_run.WeekIndex}")
```

用途：

- 当前周没有行动轴，或上一周已走完时，按周随机行动轴。
- `TimelineService.RollWeekTimeline` 筛选候选后按权重抽取。
- 抽取结果写入 `GameRun.CurrentTimelineId` 和 `TimelineLengthDays`。

这个设计较安全，因为随机结果写入了运行态和存档，读档后优先沿用已保存行动轴。

### 5.2 行动选择

入口：`WeekMapForm.RollChoices`

```csharp
GameApp.Random.DomainStream(
    SeedDomains.Action,
    $"r{run.RunActionStepIndex}_w{run.WeekIndex}_d{run.CurrentDay}_s{run.ActionStepIndex}")
```

用途：

- `ActionScheduleService.EnsureCurrentGroup` 生成整局行动组序列。
- 从当前行动组里按权重不放回抽最多 3 个行动。
- 同时随机行动耗时。

注意点：

- 行动组序列会保存到 `GameRun.ActionGroupSequence`，这部分可读档恢复。
- 但当 UI 多次打开同一步行动选择时，会再次消费同一条 action 流，导致候选行动可能变化。
- 如果希望“同一步打开多少次都看到同一组选项”，应把本次 `ActionChoice` 列表保存到运行态，或改成按 key 临时创建一次性流、不缓存消费状态。

### 5.3 行动效果

入口：`WeekLoopController.OnActionPicked`

```csharp
GameApp.Random.DomainStream(
    SeedDomains.Effect,
    $"exec_r{context.RunStepIndex}_w{_run.WeekIndex}_s{context.StepIndex}_{context.ActionGroupId}_{context.Action.Id}")
```

用途：

- 执行行动带来的随机效果。
- key 包含整局行动序号、周、本周行动序号、行动组、行动 id，隔离度较好。

### 5.4 事件

入口包括：

- 时间轴事件节点：`event/node_w{week}_d{node.Day}`
- 行动触发随机事件：`event/action_w{week}_d{day}_s{step}`
- 事件选项结算：`event/resolve_w{week}_d{day}_{eventId}`

用途：

- `EventService.RollEvent` 按权重抽事件。
- `ResolveImmediate` / `ResolveOption` 结算事件效果。

注意点：

- 不可重复事件通过 `UsedEventIds` 记录。
- 如果同一天同事件 id 被不同来源重复 resolve，`resolve_w..._{eventId}` 这条流会继续消费旧状态，而不是重新开始。是否合理取决于设计是否允许这种重复路径。

### 5.5 Boss

入口：`WeekLoopController.HandleBossNode`

```csharp
GameApp.Random.DomainStream(SeedDomains.Boss, $"w{_run.WeekIndex}")
```

用途：

- 按角色池、周限制、节点过滤、解锁条件筛选 Boss。
- 按权重抽一个。

风险点：

- key 只有周。如果同一周多个 Boss 节点都需要随机 Boss，会共用同一条流并按调用顺序继续消费。
- 当前流程 Boss 后通常会清空 pending nodes 并结束周，这个风险大概率不触发；但如果配置未来允许一周多个 Boss 节点，建议 key 加上 `node.Id` 或 `node.Day`。

### 5.6 商店

入口：`ShopForm.RollStock`

```csharp
shop: GameApp.Random.DomainStream(SeedDomains.Shop, $"w{week}_d{day}")
loot: GameApp.Random.DomainStream(SeedDomains.Loot, $"shop_w{week}_d{day}")
```

用途：

- `loot` 抽被动/主动道具。
- `shop` 抽菜品和胃部碎片。
- 道具和非道具隔离，这是正确的。

风险点：

- 商店库存只存在于 `ShopForm._stock`，没有进入 `GameRun` 存档。
- `OnOpen` 每次都会 `RollStock()`，重开同一个商店会继续消费同一条流，库存会变化。
- 购买后保存的是玩家状态，不保存剩余库存；读档后同一天再进商店，库存不一定等于离开前看到的剩余库存。

如果希望商店刷新后固定，应把商店库存按节点/行动上下文保存到运行态，直到本次商店关闭或进入下一刷新点。

### 5.7 奖励

入口：`RewardForm.OnOpen`

```csharp
GameApp.Random.DomainStream(SeedDomains.Reward, $"w{week}_d{day}")
```

用途：

- 随机金币区间。
- 抽主奖励槽位、额外奖励概率、奖励候选。

风险点：

- 奖励 offer 只存在于 UI 的 `_offer`，没有保存到 `GameRun`。
- `OnOpen` 每次都会重新生成 offer，并继续消费同一条 reward 流。
- 注释写着“按周+天派生独立随机流避免重复同一份奖励”，但如果同一天多次奖励，它们不是独立流，而是同一条流连续消费；如果 UI 重开，也会改变 offer。

建议 key 至少包含战斗 key 或行动上下文，例如 `battleKey` / `RunStepIndex` / `Action.Id`。更稳妥的是生成 offer 后保存，玩家确认前不再重掷。

### 5.8 战斗菜谱与局内战斗

入口：`BattleSessionFactory.Build`

```csharp
recipe: GameApp.Random.DomainStream(SeedDomains.Recipe, key)
combat: GameApp.Random.DomainStream(SeedDomains.Combat, key)
```

用途：

- `recipe` 生成每个菜谱槽的开局 deck。
- `combat` 提供局内战斗随机。

风险点：

- `RecipeSlotCount` 个菜谱槽共用同一条 recipe 流并连续消费。这本身可以接受，但如果未来槽位数量变化，会影响后续槽位 deck。
- 战斗过程如果允许中途保存/读档，需要保存 `RandomSnapshot` 或保存完整战斗状态，否则仅靠 seed 和 key 无法恢复战斗流的当前消费位置。

## 6. 当前测试覆盖

`RngDeterminismTests` 已覆盖：

- xoshiro 同 seed 逐位一致。
- `RandomService.Stream` 同 seed 同流名一致。
- 不同流名互不污染。
- 域流同 seed / 同 domain / 同 key 一致。
- 不同 domain / 不同 key 不同序列。
- 商店 `shop` 与 `loot` 隔离。
- `cosmetic` 不写入快照。
- `Capture` / `Restore` 后未来序列一致。

缺口：

- 没有测试 `RunPersistence` 是否保存并恢复随机流状态。
- 没有测试“同一步 WeekMap 重开，行动候选是否保持一致”。
- 没有测试“商店重开/读档后库存是否保持一致”。
- 没有测试“奖励界面重开/读档后 offer 是否保持一致”。

## 7. 问题清单

### P1：随机快照没有接入存档

代码已经有 `RandomSnapshot`、`RandomService.Capture()`、`RandomService.Restore()`，但 `RunSaveData` 没有 `RandomSnapshot` 字段。

当前 `RunPersistence.TryLoad()` 逻辑是：

```csharp
GameApp.Random.Init(data.SeedText);
GameRun run = GameRun.FromSaveData(tables, db, data);
```

这会丢失所有已创建流的消费位置。

影响：

- 依赖“同一条流连续消费”的系统，读档后会回到该流起点。
- 如果某些随机结果没有写入 `GameRun`，读档后可能重新随机出不同结果。
- 已实现的 `Capture/Restore` 测试没有覆盖真实存档链路。

建议：

- 在 `RunSaveData` 增加 `RandomSnapshot RandomSnapshot`。
- `RunPersistence.Save` 时保存 `GameApp.Random.Capture()`。
- `RunPersistence.TryLoad` 时优先 `GameApp.Random.Restore(data.RandomSnapshot)`；旧档没有快照时再 fallback 到 `Init(data.SeedText)`。

### P1：商店库存没有持久化，重开会刷新

`ShopForm.OnOpen` 每次都调用 `RollStock()`，而库存只存在 UI 内存中。

影响：

- 同一商店节点，如果 UI 被关闭后重新打开，商品可能变化。
- 购买后保存再读档，剩余库存无法恢复。
- 如果玩家可以通过返回菜单/读档反复刷新商店，会产生可刷随机。

建议：

- 将当前商店上下文和库存保存到 `GameRun`。
- 进入新商店节点/新商店行动时生成一次库存。
- 购买只修改库存状态，不重新 Roll。
- 离开商店或进入下一刷新点后清掉该库存。

### P1：奖励 offer 没有持久化，重开会重掷

`RewardForm.OnOpen` 每次都调用 `RewardGranter.GenerateOffer()`，offer 只存在 UI 字段中。

影响：

- 奖励界面重开可能改变金币、主奖励、额外奖励。
- 如果领奖前保存/崩溃/回菜单，读档后奖励可能变化。

建议：

- 战斗胜利结算时生成并保存 `PendingRewardOffer`。
- `RewardForm` 只展示 pending offer。
- 玩家确认领取后应用并清空 pending offer。

### P2：部分 key 粒度偏粗

例子：

- `Reward` 使用 `w{week}_d{day}`，同一天多场奖励共用同一流。
- `Boss` 使用 `w{week}`，同一周多 Boss 节点共用同一流。
- `Shop` 使用 `w{week}_d{day}`，同一天多个商店来源共用同一流。

共用流不一定错，但它会让结果依赖调用顺序和打开次数。

建议：

- 奖励 key 加战斗 key 或行动上下文。
- Boss key 加 node id / day。
- 商店 key 加来源，如 `nodeId`、`actionRunStep` 或显式 shop instance id。

### P2：UI 打开时直接消费玩法随机

当前 `WeekMapForm`、`ShopForm`、`RewardForm` 都在 `OnOpen` 里消费随机。

影响：

- UI 生命周期会影响玩法结果。
- 重开、刷新、异常关闭、读档重进，都可能改变随机消费。

建议：

- 玩法随机尽量在编排层/服务层生成，并写入运行态。
- UI 只展示已生成结果。
- 如果只是预览，不应推进玩法随机流。

### P3：非法整数区间静默返回 min

`Range(int minInclusive, int maxExclusive)` 对非法区间返回 `minInclusive`。

影响：

- 配置错误不容易暴露。

建议：

- 玩法配置随机可以保留容错，但在编辑器测试或开发构建中记录 warning。
- 或者新增严格版 API，例如 `RangeStrict`。

## 8. 建议改造顺序

1. 先把 `RandomSnapshot` 接入 `RunSaveData` 和 `RunPersistence`，保证真实读档链路能恢复随机流状态。
2. 给存档链路补测试：保存前消费若干流，读档后继续抽，结果必须一致。
3. 把商店库存改为运行态 pending 数据，防止重开刷新。
4. 把奖励 offer 改为运行态 pending 数据，防止重开重掷。
5. 梳理所有 `DomainStream` key，给同一天/同周可能多实例的系统补充 instance id。
6. 增加 UI 重开测试：同一步行动选择、同一个商店、同一次奖励，在重开后展示应保持一致。

## 9. 当前可接受的部分

以下部分目前没有明显问题：

- PRNG 算法固定，适合确定性玩法随机。
- 字符串种子哈希稳定。
- 浮点 `[0,1)` 生成方式常规。
- 整数区间使用无偏算法。
- 权重随机忽略非正权重，业务层按需兜底为 1。
- `cosmetic` 域从快照排除的设计合理，前提是它绝不参与玩法判定。
- 没发现 `Assets/GameMain/Scripts` 下有玩法代码直接使用 `UnityEngine.Random`、`System.Random` 或 `Random.Range`。

## 10. 一句话总结

随机底座质量是可以的，问题主要不在 PRNG，而在“随机结果何时生成、是否保存、读档后从哪里继续”。如果目标是严谨复现，下一步应优先打通 `RandomSnapshot` 存档，并把商店/奖励/行动选择这类 UI 触发随机改成运行态 pending 结果。
