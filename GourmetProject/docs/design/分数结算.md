# 分数结算规则与扩展性

> 面向策划。说明「吃」这一步分数是怎么算出来的、结算按什么顺序执行、标签效果有哪些、以及后续怎么加新效果 / 新来源。
>
> 对应代码目录：`Assets/GameMain/Scripts/Gameplay/Scoring/`。结算层是纯 C#，可单测、同种子可复现，表现层只读取结果做演出。

---

## 1. 一句话理解

分数结算采用「小丑牌式阶段结算」：
**逐道菜结算，每道菜各算各的贡献，全部菜算完后再做一次全局修正，最后取整得到总分。**

不是「全局事件广播」，而是**确定性、可预测、可解释**的流水线。同一个棋盘 + 同一套配置，结算结果永远一致。

---

## 2. 单道菜的计算公式

每道菜有两个累加器：**加法区（FlatBonus）** 和 **乘区（Multiplier）**。

```
本菜贡献 = (基础美味度 + 加法区累加值) × 乘区累乘值
```

- **基础美味度**：菜品自身的固定分（`DishDef.Deliciousness`）。
- **加法区**：所有「+X 美味度」类效果累加，初始为 0。
- **乘区**：所有「×X」类效果连乘，初始为 1。

> 关键规则：**先把所有加法加完，再乘乘区。** 加法和乘区不会交错影响，所以「先加后乘」的结果是确定的。

### 算例

一道菜：美味度 10，带「新鲜（+5 美味度）」和「香甜（×1.5）」两个标签。

```
(10 + 5) × 1.5 = 22.5
```

---

## 3. 总分公式

所有菜的贡献先求和，再叠加**局级修正**，最后取整：

```
总分 = 四舍五入( (所有菜贡献之和 + 局级加法) × 局级乘区 )
```

- **所有菜贡献之和**（`RawSum`）：每道菜按第 2 节算出贡献后相加。
- **局级加法 / 局级乘区**（`FinalFlat` / `FinalMultiplier`）：作用于「全部菜的总和」这一层，由遗物、周规则、道具 Buff 注入。默认加法 0、乘区 1。
- **取整规则**：四舍五入到整数，**0.5 向上进位**（例如 22.5 → 23）。只有最终总分取整，过程中全部用浮点保留精度。

### 算例

两道菜贡献分别是 22.5 和 30，本局有一个「全局 ×2」的遗物：

```
(22.5 + 30 + 0) × 2 = 105  → 总分 105
```

## 4. 结算顺序（最重要的规则）

### 4.1 阶段顺序

结算分成若干阶段，按下表从上到下依次执行：

| 阶段 | 说明 | 作用范围 |
| --- | --- | --- |
| `BeforeAll` | 全部开始前 | 全局 |
| `BeforeDish` | 每道菜结算前 | 逐菜 |
| `DishBase` | 记录该菜基础美味度 | 逐菜 |
| `DishTags` | 结算**食品标签** | 逐菜 |
| `CellTags` | 结算**棋盘格标签** | 逐菜 |
| `AfterDish` | 每道菜结算后 | 逐菜 |
| `AfterAllDishes` | 全部菜结算完 | 全局 |
| `Final` | 局级修正 | 全局 |

「逐菜」阶段会对**每一道菜**各跑一遍；「全局」阶段整局只跑一次。

> 设计含义：**同一道菜内，食品标签先于格子标签结算。**

### 4.2 菜与菜之间的顺序（棋盘顺序）

逐菜阶段按棋盘位置遍历：**从上到下、从左到右**（先比行 Y，再比列 X，最后比放置 id）。所以靠左上角的菜先结算。

### 4.3 同一阶段内的顺序

当同一阶段里有多个效果时，按以下优先级稳定排序（前者优先）：

1. **阶段**（`Phase`）
2. **棋盘顺序**（`BoardOrder`，左上优先）
3. **来源类型**（`Dish` → `DishTag` → `CellTag` → `BoardTag` → `Relic` → `WeekModifier` → `FinalModifier`）
4. **优先级**（`Priority`，数字小的先执行，可正可负）
5. **登记序号**（`Sequence`，先收集到的先执行）

> 策划要点：如果两个效果在同一阶段、需要明确先后，用**优先级**字段控制（小的先）。不要依赖「配置表的行顺序」之外的隐性约定。

## 5. 标签效果类型（现有内置）

标签在配置里用 `EffectType`（效果类型）+ `EffectValue`（效果数值）描述。当前内置 6 种：

| EffectType | 含义 | 公式（X = EffectValue） |
| --- | --- | --- |
| `AddFlat` | 本菜加法区 +X | 加法 += X |
| `AddMult` | 本菜乘区 ×X | 乘区 ×= X |
| `PerAdjacentDish` | 每个相邻菜，本菜 +X | 加法 += X × 相邻菜数量 |
| `PerEmptyCell` | 棋盘每个空格，本菜 +X | 加法 += X × 棋盘空格数 |
| `PerOccupiedCell` | 本菜每占一格，本菜 +X | 加法 += X × 本菜占格数 |
| `PerDishOnBoard` | 棋盘每多一道菜，本菜乘区按复利涨 | 乘区 ×= (1 + X) 的「棋盘菜数」次方 |

其中 `PerDishOnBoard` 是复利：棋盘上有 N 道菜时，乘区因子为 `(1 + X)^N`。

> 还有两个「局级效果」（不挂在食品标签上，给遗物 / 周规则用）：
> - `AddFinalFlat`：总分加法区 +X（作用在 `Final` 阶段）。
> - `MultiplyFinal`：总分乘区 ×X（作用在 `Final` 阶段）。

### 配置字段说明

标签定义（`TagDef`，来自 Luban 配置 `TbTag`）相关字段：

| 字段 | 用途 |
| --- | --- |
| `EffectType` | 效果类型，对应上表 |
| `EffectValue` | 效果主数值 X |
| `EffectParam` | 效果次要参数（如分类过滤、目标标签 id），多数效果用不到 |
| `Category` | 标签分类：固有 / 唯一A / 唯一B |
| `TermId` | 关联专有名词 id，非空时菜品详情额外展示 |

## 6. 可解释性（给 UI / 调试 / 数值验证）

每次结算输出两类记录，方便做结算演出、复盘和数值校对：

- **结算明细（`ScoreLine`）**：记录「**哪个来源**在**哪个阶段**对**哪道菜 / 哪一格**做了什么改动」，含改动前后数值。例如「新鲜：美味度 +5」。
- **生命周期事件（`ScoreEvent`）**：记录「发生了什么」的时间线（开始结算、某道菜开始 / 完成、某效果开始 / 结束、命令执行），不直接改分数，用于演出和回放。

> 数值需求：每加一个新效果，都应保证它在明细里能被解释清楚（来源、阶段、数值），否则 UI 无法展示、QA 无法验证。

## 7. 扩展性：后续怎么加东西

结算管线设计成「**加效果不用改结算器**」。常见的三种扩展：

### 7.1 加一个新的标签效果类型

适用：想要一种全新的「数值规则」（例如「每有一个同类菜 +X」）。

1. 在 `TagEffectType` 枚举（配置侧 + 玩法侧）新增一项。
2. 写一个实现 `ITagEffect` 的效果类，在 `Apply` 里通过 `ctx.AddFlat() / ctx.MultiplyBy()` 等改分。
3. 在 `TagEffectRegistry.CreateDefault()` 注册映射。
4. 配置表里给标签填上新的 `EffectType`。

策划侧只需要：确定**公式**、**用哪个数值字段**（`EffectValue` / `EffectParam`）、以及它**属于哪个阶段**（一般食品标签都在 `DishTags`）。

### 7.2 加遗物 / 周规则 / 道具这类「非食品标签」来源

适用：效果不挂在某个菜上，而是「本局生效」「满足条件触发」。

实现一个 `IScoreEffectSource`，把它要产生的效果收集成若干条目（指定**阶段**、**来源类型**、**作用对象**、**优先级**）。例如：

- 「全局结算分 ×2 的遗物」→ 在 `Final` 阶段产出一个 `MultiplyFinal` 效果。
- 「每道菜额外 +2 的撒盐遗物」→ 在 `AfterDish` 阶段产出一个逐菜加法效果。

这些来源在创建 `BattleSession` / `ScoreCalculator` 时注入，不污染食品标签体系。

> 当前 `BattleSession` 已经预留了 `FinalFlat` / `FinalMultiplier` 两个局级修正入口，简单的「整局加分 / 整局乘区」道具可以直接写这两个值，不必新建来源。

### 7.3 连锁效果（触发时再触发一个效果）

适用：「某效果触发时，额外引发另一个效果」。

效果内部通过 `ctx.SubmitCommand(new ResolveScoreEffectCommand(另一个效果条目))` 提交连锁，结算器会在当前效果结束后立即解析它，并正确归属到当前来源 / 阶段 / 格子，明细不会错位。

> 安全阀：单次结算的命令执行数有上限（防止效果互相无限触发）。设计连锁时避免出现环形互相触发。

## 8. 红线与约束

- **结算层不写具体玩法内容的硬编码分支**：新规则走「新效果 + 注册」或「新来源」，不要往结算器里塞 `if (标签 == "辣条")`。
- **结算层保持纯 C#**：不引用 Unity / GameFramework，保证可单测、可复现。
- **改分只能走上下文**：效果通过 `AddFlat / MultiplyBy / AddFinalFlat / MultiplyFinalBy / SubmitCommand` 改分，不要绕过上下文直接改结果，否则明细会缺失。
- **新效果必须配套测试**：至少覆盖总分、执行顺序或明细来源（参考 `Tests/EditMode/ScoreCalculatorTests.cs`）。
- **顺序依赖要显式**：同阶段先后用 `Priority` 表达，不要依赖隐性顺序。

## 9. 关键类速查

| 类 / 文件 | 职责 |
| --- | --- |
| `ScoreCalculator` | 编排：收集效果 → 按阶段 / 顺序稳定执行 → 输出结果 |
| `ScoreSnapshot` | 一次结算的只读输入（棋盘、配置、局级修正、额外来源） |
| `ScoreContext` | 结算过程中的可变累加器（加法区 / 乘区 / 总分修正），并产出明细与事件 |
| `IScoreEffect` / `ITagEffect` | 统一效果接口；标签、格子、遗物、周规则最终都实现它 |
| `TagEffectRegistry` | 把 `EffectType` 派发到具体效果实现 |
| `IScoreEffectSource` | 把某类来源（食品标签 / 遗物 / 周规则…）转换成效果条目 |
| `ScoreResult` | 结算结果：逐菜明细、`RawSum`、局级修正、`Total`、`ScoreLine`、`ScoreEvent` |
| `ScorePhase` | 阶段枚举（决定默认执行顺序） |
