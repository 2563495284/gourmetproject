# 局外框架设计 - Cursor 实现总结

> 来源：飞书文档《局外框架设计》  
> 目标：把原始设计整理成可交给 Cursor/工程实现的 Markdown 需求说明。

## 1. 设计目标

本系统是一个偏肉鸽的局外框架，核心目标：

- 提供**强随机**、**强构筑**、有新鲜感的肉鸽体验。
- 让玩家根据随机化场景做出有意义的决策。
- 单局游戏持续多周，每周是一个阶段，通过行动轴推进。
- 玩家在每周不断进行“三选一”行动选择，行动会消耗对应天数。
- 行动结束后，如果行动轴经过特殊节点，则触发对应特殊事件。

---

## 2. 核心玩法循环

### 2.1 单局结构

```text
开始准备
  ↓
选择/确认角色
  ↓
初始化菜谱、道具池、行动轴
  ↓
进入第 1 周
  ↓
每次从 3 个行动中选择 1 个
  ↓
执行行动并推进天数
  ↓
检查是否经过行动轴特殊节点
  ↓
触发节点事件 / 商店 / Boss / 利息等
  ↓
进入下一周或结算胜负
```

### 2.2 周阶段

- 单局持续多周。
- 一周对应一个行动轴阶段。
- 行动轴一般是 7 天长度。
- 玩家选择行动后，行动轴按行动消耗的天数向前推进。
- 进度条结束时：
  - 若未达到最终周：进入下一周。
  - 若完成最终 Boss：游戏胜利。

## 3. 开始准备

### 3.1 角色

每个角色需要配置：

| 字段 | 说明 |
|---|---|
| 初始被动道具 | 角色进入单局时自带的被动道具 |
| 菜品随机池 | 当前角色可随机到的菜品集合 |
| 道具随机池 | 当前角色可随机到的道具集合 |
| 胃部大小 | 用长、宽配置，影响可容纳内容 |
| 行动轴库 | 当前角色可随机到的行动轴配置集合 |
| Boss 池 | 当前角色可能遇到的 Boss 集合 |

### 3.2 菜谱

- 每个角色对应一个菜谱。
- 进入游戏时，从菜谱中随机若干菜品作为初始菜品。
- 玩家可以选择菜谱表皮，即难度。
- 不同难度会带来：
  - 机制变化。
  - 数值修改。
  - 美食奖励差异。

---

## 4. 行动系统

### 4.1 行动选择

每轮给玩家展示 3 个可选行动，玩家选择 1 个执行。

行动可能包括：

- 事件行动。
- 美食行动。
- 奖励行动。
- 负面事件。
- 商店相关行动。
- 其他待扩展行动。

每个行动至少需要包含：

| 字段 | 说明 |
|---|---|
| action_id | 行动唯一 ID |
| action_type | 行动类型 |
| cost_days | 消耗天数 |
| weight | 随机权重 |
| preconditions | 出现前置条件 |
| repeatable | 是否可重复出现 |
| payload | 行动具体内容配置 |

### 4.2 事件行动

事件行动配置要点：

| 配置项 | 说明 |
|---|---|
| 前置条件 | 满足条件后才有概率随机出 |
| 权重 | 随机到该类事件的权重 |
| 权重序列 | 部分事件满足条件时，每次随机使用序列中的下一个权重或事件 |
| 是否可重复 | 部分事件不可重复随机到 |
| 分类 | 奖励事件、负面事件、美食事件等 |
| 选项 | 玩家需要选择选项，不同选项产生不同结果 |
| 结果 | 可能给予美食、奖励、Buff 等 |

事件执行流程：

```text
检查前置条件
  ↓
根据权重进入随机池
  ↓
展示事件文本与选项
  ↓
玩家选择选项
  ↓
执行对应结果
  ↓
更新局内状态
```

---

## 5. 美食系统

### 5.1 美食外观

- 美食外观根据固定奖励分为多种图标。
- 不同难度下，美食分为两种，奖励也不同。

### 5.2 美食玩法

- 进入局内美食挑战。
- 玩家需要完成要求分数。
- 达成目标后获得奖励。
- 若任意一次美食中未完成目标分数，则游戏失败。

美食行动建议字段：

| 字段 | 说明 |
|---|---|
| food_id | 美食 ID |
| icon_type | 图标类型，依据固定奖励分类 |
| difficulty_variant | 难度变体 |
| target_score | 目标分数 |
| reward | 达成奖励 |
| fail_condition | 失败条件，默认未达目标分 |

---

## 6. 奖励系统

- 奖励小概率出现。
- 只随机奖励事件。
- 奖励可能来自：
  - 事件选项。
  - 美食达成。
  - 商店购买。
  - Boss 击败。
  - 节点事件。

奖励类型建议：

- 金币。
- 菜品。
- 主动道具。
- 被动道具。
- Buff。
- 胃部格子。
- 解锁内容。

---

## 7. 胜负与结算

### 7.1 胜利条件

- 完成第 N 周的 Boss 后，游戏胜利。

### 7.2 失败条件

- 任意一局美食中，未完成目标分数，则游戏失败。

### 7.3 结算流程

```text
判定胜负
  ↓
展示胜负结果
  ↓
展示局内指标
  ↓
玩家确认
  ↓
展示新解锁的道具、菜品等内容
  ↓
返回局外
```

结算页需要展示：

- 胜利 / 失败。
- 当前周数。
- 击败 Boss 情况。
- 获得金币。
- 获得/使用菜品。
- 获得/使用道具。
- 触发事件数量。
- 新解锁内容。

---

## 8. 商店系统

### 8.1 商店刷新

- 商店根据进度存在隐藏分。
- 隐藏分用于随机菜品、道具等商品。

### 8.2 商店售卖内容

商店可售卖：

- 菜品。
- 主动道具。
- 被动道具。
- 胃部格子。

### 8.3 商店操作

玩家在商店中可以：

- 购买商品。
- 编辑菜谱。
- 删除菜品。

删除菜品需要花费金币。

商店商品建议字段：

| 字段 | 说明 |
|---|---|
| item_id | 商品 ID |
| item_type | 菜品 / 主动道具 / 被动道具 / 格子 |
| price | 价格 |
| hidden_score_range | 隐藏分区间 |
| weight | 随机权重 |
| stock | 库存 |

---

## 9. 阶段与行动轴

### 9.1 初始行动轴

- 初始行动轴是一个 7 天的轴。
- 整天位置上可能有特殊节点。
- 进度条结束时进入下一周，或判定游戏胜利。
- 行动轴长度可能受到道具、角色、事件影响。

### 9.2 节点事件

特殊节点展示在行动轴上，常见类型包括：

| 节点类型 | 说明 |
|---|---|
| Boss | 带特殊机制的美食行动 |
| 收取利息 | 根据当前金币数，每满 N 金币获得 1 金币 |
| 进入商店 | 进入商店购买、编辑、删除菜品 |
| 其他 | 待补充更多节点事件 |

### 9.3 执行顺序

行动执行后，如果进度条前进区间内包含节点事件，则需要结算这些节点事件。

```text
执行行动
  ↓
推进行动轴
  ↓
检测经过的节点
  ↓
按顺序触发节点事件
  ↓
节点事件全部结算后继续下一次行动选择
```

如果一次行动跨过多个节点，建议按行动轴从前到后的顺序依次结算。

### 9.4 行动轴随机

- 根据角色预设多种行动轴库。
- 每次根据权重随机一个行动轴配置。
- 每种配置包含若干节点事件。
- Boss 除外，Boss 走独立随机逻辑。

行动轴配置建议：

```json
{
  "timeline_id": "timeline_001",
  "role_id": "role_001",
  "weight": 100,
  "base_length_days": 7,
  "nodes": [
    {
      "day": 3,
      "node_type": "interest",
      "payload": {
        "gold_per_threshold": 1,
        "threshold": 10
      }
    },
    {
      "day": 5,
      "node_type": "shop"
    }
  ]
}
```

## 10. Boss 随机

Boss 随机规则：

- 按权重随机。
- 部分 Boss 需要满足特殊条件才解锁。
- 根据角色筛选可随机的 Boss。
- Boss 带有特殊机制。
- 完成第 N 周 Boss 后获得胜利。

Boss 配置建议字段：

| 字段 | 说明 |
|---|---|
| boss_id | Boss ID |
| role_pool | 可出现角色池 |
| unlock_conditions | 解锁条件 |
| weight | 随机权重 |
| week | 出现周数或阶段 |
| food_config | Boss 对应的美食挑战配置 |
| special_mechanics | Boss 特殊机制 |

## 11. 推荐工程模块拆分

给 Cursor 实现时，可以按以下模块拆：

```text
RoguelikeGameManager
  - 管理单局生命周期
  - 初始化角色、菜谱、行动轴
  - 管理胜负与结算

RoleConfigService
  - 读取角色配置
  - 提供角色菜品池、道具池、胃部大小、行动轴池、Boss 池

RecipeService
  - 初始化菜谱
  - 编辑菜谱
  - 删除菜品

ActionRandomService
  - 根据前置条件、权重、是否重复生成三选一行动
  - 处理权重序列

ActionExecutor
  - 执行行动结果
  - 推进天数
  - 修改局内状态

TimelineService
  - 初始化行动轴
  - 推进行动轴
  - 检测经过节点
  - 触发节点事件

EventService
  - 展示事件
  - 执行事件选项结果

FoodChallengeService
  - 处理美食挑战
  - 判断分数是否达标
  - 发放奖励或触发失败

ShopService
  - 根据隐藏分刷新商品
  - 处理购买、编辑菜谱、删除菜品

RewardService
  - 统一发放金币、菜品、道具、Buff、解锁内容等

SettlementService
  - 生成胜负结算数据
  - 展示新解锁内容
```

## 12. 推荐核心状态结构

```ts
type RunState = {
  runId: string;
  roleId: string;
  difficultyId: string;

  currentWeek: number;
  currentDay: number;
  timelineLengthDays: number;

  gold: number;
  hiddenScore: number;

  recipe: FoodId[];
  activeItems: ItemId[];
  passiveItems: ItemId[];
  buffs: BuffId[];

  usedEventIds: string[];
  completedBossIds: string[];

  timeline: TimelineNode[];

  result?: "playing" | "win" | "lose";
};

type TimelineNode = {
  day: number;
  nodeType: "boss" | "interest" | "shop" | "event";
  payload?: any;
  triggered?: boolean;
};
```

## 13. 关键实现规则

1. 进入单局时，先按角色初始化：
   - 初始被动道具。
   - 初始菜谱。
   - 菜品随机池。
   - 道具随机池。
   - 胃部大小。
   - 行动轴。

2. 每次行动选择必须是三选一。

3. 行动随机需要过滤：
   - 前置条件不满足的事件。
   - 不可重复且已出现过的事件。
   - 角色/难度不匹配的行动。

4. 行动执行后先推进天数，再检查经过的行动轴节点。

5. 如果一次行动经过多个节点，应按节点在行动轴上的顺序依次结算。

6. 美食挑战未达目标分，立即失败。

7. 完成第 N 周 Boss，立即胜利。

8. 商店商品根据隐藏分和权重随机。

9. 删除菜品需要扣除金币。

10. 结算时先展示胜负和局内指标，再展示新解锁内容。

可以直接把下面这段交给 Cursor：

